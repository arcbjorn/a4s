# Operations and disposable-node runbook

This runbook covers the current vertical slice. It is not a production install
guide. The only authorized target is a disposable Linux host or VM whose
containerd namespace and test workloads can be safely inspected and discarded.

## Current process model

There is one binary with two distinct modes relevant to operations:

- `simulate` runs a finite reconciliation in one process using memory state.
- `node` opens containerd and a durable ledger, then processes signed JSON
  envelopes from standard input until EOF or the first error.

There is no a4s server, socket listener, systemd unit, heartbeat, or background
supervisor yet.

## Host prerequisites

Confirm before starting:

- Linux architecture matches the built binary.
- containerd 2.x and runc are installed and healthy.
- A snapshotter is configured and can unpack the target image.
- The test image is pinned by a real registry digest.
- The operator can access the containerd socket.
- The node ID is unique for the experiment.
- System time is synchronized closely enough for short-lived envelopes.
- No production workload uses the `a4s` containerd namespace.

Recommended dedicated paths:

```text
/etc/a4s/                     trusted public keys and configuration
/var/lib/a4s/                 node ledger and future state
/var/log/a4s/allocations/     allocation stdout and stderr
/usr/local/bin/a4s            binary
```

Directories should be owned by the dedicated service identity when that
identity exists. The current process generally needs privileged containerd
socket access, so isolate the experiment at the host level.

## Build artifact

On a trusted build host at the project root:

```bash
go test -race ./...
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -trimpath -o build/a4s-linux-amd64 ./cmd/a4s
```

Transfer the binary and record its SHA-256 checksum through your normal secure
copy channel. This project does not yet provide signed releases.

## Signing-key setup

The node expects a file containing the raw 32-byte Ed25519 public key encoded as
standard or unpadded base64. The matching private key belongs to the future
controller and must not be copied to the node.

For the disposable experiment, use an ephemeral key generated by a small local
test driver based on `ed25519.GenerateKey` and `node.Sign`, following
`node/dispatcher_test.go`. Do not commit the generated key or place it in a
scenario. Delete it after the experiment using your host's approved secure-key
handling process.

The absence of a production key-enrollment tool is intentional and recorded as
a blocker. Do not invent an ad hoc long-lived trust process around the stream
harness.

## Start the node harness

```bash
/usr/local/bin/a4s node \
  --node-id edge-1 \
  --key-id control-test-1 \
  --public-key /etc/a4s/control-test-1.pub \
  --ledger /var/lib/a4s/node-ledger.jsonl \
  --containerd /run/containerd/containerd.sock \
  --namespace a4s \
  --log-dir /var/log/a4s/allocations
```

Standard input must remain connected to the signed-envelope producer. Standard
output is machine-readable `DispatchResult` JSON. Send human diagnostics from
the surrounding harness to a separate log so it does not corrupt the stream.

The node performs a five-second containerd health check before reading input.
It exits on:

- Invalid CLI configuration or public key.
- Unavailable containerd.
- Corrupt ledger replay.
- Malformed JSON or unknown fields.
- Invalid signature, node target, or time window.
- Idempotency conflict.
- Runtime failure.
- Output encoding failure.

This fail-fast behavior is suitable for the experiment but needs per-message
error responses and supervision before daemon use.

## Smoke-test sequence

Use a real, low-risk image that exits slowly or serves a local port. Submit
three separately signed envelopes with ordered semantic intent:

1. `pull_image` with the real digest reference and target node.
2. `create_allocation` with a DNS-style allocation ID, workload, image, and
   positive resource limits.
3. `start_allocation` for that allocation.

Each envelope needs a unique ID and idempotency key, the same goal/proposal
lineage as appropriate, a node ID matching the harness, and a validity window
no longer than five minutes.

Expected evidence kinds are:

```text
image.present
allocation.created
allocation.running
```

Running is not ready. Independently inspect the process or application for the
experiment; do not feed that manual observation into a production claim.

## Read-only inspection

If `ctr` is installed and configured for the same containerd socket, inspect
only the dedicated namespace:

```bash
ctr --namespace a4s containers list
ctr --namespace a4s tasks list
```

Confirm:

- Exactly one container exists for the allocation ID.
- It has `a4s.io/managed=true`, the expected workload, and exact image labels.
- The task PID matches returned evidence.
- Allocation output appears only under the configured log directory.
- The ledger is mode `0600` and contains no secret value.

Do not use broad cleanup commands from this document. Resolve exact test
container, task, and snapshot identities and use the disposable host's normal
recovery or teardown process.

## Restart and replay test

1. Preserve the ledger.
2. Stop and restart only the `a4s node` harness.
3. Resubmit the exact same signed envelopes before they expire, or generate new
   envelopes only if the idempotency semantics being tested are clearly
   defined.
4. Confirm exact repeats return the stored envelope digest and evidence without
   creating another container or task.
5. Submit a different envelope using a previously committed idempotency key and
   confirm rejection.

Because expired envelopes are rejected before ledger lookup, an exact replay
after expiry currently fails rather than returning historical evidence. Record
whether the future transport should authenticate an expired retry through a
different recovery query instead of weakening expiry checks.

## Data requiring backup

Current durable files:

| File | Purpose | Recovery behavior |
|---|---|---|
| Controller event JSONL | Intent, decisions, evidence, audit chain | Replay verifies sequence and hashes |
| Node ledger JSONL | Successful idempotency results | Replay restores deduplication |
| Allocation logs | Workload diagnostics | Not control authority |

containerd metadata and snapshots are external state. The future server must
reconcile them against durable goals and observations; they are not a
replacement for the event log.

Backups must preserve file order and contents. Copying a file while it is being
appended can produce an incomplete last record; coordinate a writer pause or
use a storage snapshot. Restore must be tested by opening and replaying the
file before resuming mutation.

## Failure response

### Event log corruption

Stop mutation. Preserve the corrupt file and an independent copy. Do not remove
or rewrite the offending line to make startup pass. Determine whether the cause
is partial write, storage failure, accidental edit, or compromise. Restore a
verified backup and reconcile missing dispatched actions through node ledgers
before reissuing anything.

### Node ledger corruption

Stop the node harness. Preserve the file. Without the ledger, retries may reach
the backend again; the three current container actions are designed to be
idempotent, but this is not a general recovery guarantee. Inspect exact
containerd state before restoring or reconstructing ledger data.

### Dispatched event without completion

Query the target node's idempotency result once the future transport supports
it. If absent, observe containerd state before retrying the same semantic action
with a well-defined idempotency identity. Never assume failure solely from a
missing completion event.

### Controller unavailable

Existing containerd tasks continue. The current node harness has no restart
supervisor or desired-state lease enforcement. Future node behavior should
retain last accepted allocations while refusing expired new actions.

### Node unavailable

Do not place a duplicate stateful workload. v1alpha1 rejects stateful goals for
this reason. Stateless relocation is also not implemented yet.

## Productionization sequence

Before installing a persistent systemd service:

1. Add a real node transport with mutual authentication.
2. Add per-message errors instead of process exit.
3. Add signal handling and graceful shutdown.
4. Add orphan discovery and restart reconciliation.
5. Add independent liveness/readiness probes.
6. Add least-privilege service identity and host sandboxing.
7. Add key enrollment, rotation, and revocation.
8. Add logs and metrics that never contaminate the protocol stream.
9. Complete the security checklist and destructive lifecycle actions.
